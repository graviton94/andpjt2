## 승인 대상 상품과 산식

| 보유 단계 | 누적 구매가 | 상한 적용 전 상시 P 증가 | 조건을 모두 충족하면 |
|---|---:|---:|---:|
| 1개 | ₩3,300 | +0.50% | +0.75% |
| 3개를 여러 세트에 분산 | ₩9,900 | +1.50% | +2.25% |
| 1세트 완성 | ₩9,900 | +2.25% | +3.00% |
| 2세트 완성 | ₩19,800 | +4.50% | +6.00% |
| 8개 보유 | ₩26,400 | +5.50% | +7.50% |
| 3세트 전부 완성 | ₩29,700 | +7.75% | +10.00% |

프리즘은 연쇄·과부하·합치기, 리부트는 유효 초기화·현재 회차 Lv25·유효 GB 동기화, 스튜디오는 활성 앱 4개·프리미엄 ★ 장착·프로 앱 장착이 각 아이템의 별도 조건이다. 출시 후보 아홉 SKU와 표시 이름은 상세 제안서의 표를 기준으로 리뷰한다. [아이템별 발동 조건](cosmetics-proposal.md)

가산율은 정수 bp 단위로 계산한다. 1bp는 0.01%p다. `b = 50 × 보유 수 + 25 × 발동한 보유 SKU 수 + 75 × 완성 세트 수 + 100 × 전체 완성 여부`다. 기존 효과까지 적용한 스와이프 P가 `P`, 기존 레벨 상한 여유가 `R`이면, 최종 지급 `min(R, floor(P × (10,000 + b) / 10,000))`에서 기존 지급 `min(R, P)`를 뺀 값이 화면에 표시할 EX 추가 P다. 예를 들어 `P = 1000`, `R = 1050`, `b = 1000`이면 최종 1050 P, 실제 EX 추가는 50 P다.

## 승인 후 작업 순서

| 순서 | 대상 | 작업과 산출물 |
|---|---|---|
| 1 | `Rules.kt`, `Monetization.kt`, `Save.kt` | 가격·SKU·세트·발동 식별자를 `RuleSet.commerce` 쪽에 한 번 정의한다. `Account`에 빈 집합 기본값으로 EX 보유 SKU를 기록하고, 세트 진척과 상시·최대 가산은 이 집합으로 계산한다. 옛 저장에서 기본값으로 열 수 있으면 버전 1을 사용한다. |
| 2 | `Engine.kt`, `Meta.kt` | 일반·자동 스와이프의 기존 효과 계산 후 레벨 상한 직전 한 지점에서 EX를 적용한다. 연쇄 조건은 기존 결과의 폭발 + 과부하 파동 수를 사용한다. 지갑·회차 P·개인 최고 기록·최근 수입률에 기존 정산 경로를 통해 반영하고, 오프라인·시간 도약은 최근 수입률을 통해 반영한다. 고정 시드 일일 도전은 기존 공용 판을 사용한다. |
| 3 | `Monetization.kt`, `WebSession.kt`, 앱 브리지 | 알려진 미보유 SKU와 유효한 거래만 처리한다. 기존 `claimOnce`와 보유 SKU를 같은 상태 갱신에 반영한다. 빈 영수증, 중복 구매, 동일 영수증 재전송, 다른 SKU에 재사용된 거래를 각각 검증한다. 디버그 거래는 기존 브리지의 디버그 검사로 제한한다. 실제 Play 연동 단계의 복원·환불은 검증된 보유 상태를 동기화하고 세트를 다시 계산한다. |
| 4 | `WebSession.kt`, `api-changes.md`, 화면 담당 | `bm()`에 SKU·가격·개별 효과·세트 진척·구매 후 예상치를 추가하고, 스냅샷에는 간결한 보유 효과와 진척을 추가한다. 스와이프 결과는 발동 조건과 실제 EX 추가 P를 덧붙인다. P는 기존과 같은 10진 문자열, 가산은 정수 bp, 가격은 원 단위를 제안한다. 기존 JSON 계약을 유지하면서 예시 응답을 화면 담당에게 넘긴다. |
| 5 | `tools/economy-sim`, 코어 테스트, Android CI | 운영 코어와 시뮬레이터가 같은 SKU 카탈로그와 정산을 호출하게 연결한다. 고정 시드 테스트와 기기 거래·복원 검증을 완료하고 원자료·판정표·Actions 아티팩트를 제출한다. |

구매 확인 화면에는 결제 가격, 고유 효과의 조건, 상시 가산, 해당 구매로 완성되는 세트의 추가 가산을 함께 보여준다. 구매 가격과 효과에 대한 판단은 코어 상품표에서 공급하고, 웹 시각 디자인과 외형 제작은 화면 담당과 조율한다.

## 구현 후 검수 기준

- **정산**은 동일 상태에서 EX 구매 집합을 0·1·3·6·9개로 증가시켜 비교한다. 한 세트와 분산 구매를 구분하고, 조건 발동·미발동, 상한에 일부나 전부 막히는 지급, 자동 스와이프, 일일 도전의 고정 점수를 확인한다.
- **구매와 저장**은 옛 저장, 앱 재실행, 공장 초기화, GB 동기화, 동일 영수증 재전송, 이미 산 SKU 추가 요청에 대해 보유권과 가산율이 일관적인지 확인한다. EX 9종과 기존 1년 광고 사용을 넣어 20KB 저장 기준을 다시 잰다. 저장 성공 여부가 거래 확인에 반영되는지 확인한다. Play 연동 후에는 보유·환불 반영과 세트 해제를 따로 확인한다.
- **진행**은 먼저 현재 미보유와 풀세트 비교를 동일한 10개 시드로 운영 코어에서 재현한다. 이후 1·2세트 및 세션 중 순차 구매 조건을 추가하고 최초 환생일, Lv124, 가산 발동 빈도를 기록한다. 화면 제공 보상만 사용한 시나리오는 그 정책을 명시한다. 하한보다 빨리 도달한 시드와 상한 이후 도달하거나 미도달한 시드는 각각 집계한다.
- **기기**는 `./gradlew -p core test`와 `.github/workflows/android.yml`을 사용한다. 디버그 APK의 구매 확인·거래·정산·재실행을 검증하고 스크린샷, 저장 JSON, 구매 전후 API 응답을 남긴다. 기기 화면 검증 범위는 화면 담당이 연결한 UI를 기준으로 기록한다.

## 사용자 결정 요청

1. 제품 구성과 가격을 **프리즘·리부트·스튜디오 3세트 × 3개, 개당 ₩3,300**으로 승인할지 결정한다.
2. 효과 구조를 **보유 상시 +0.50%p, 아이템 조건 +0.25%p, 세트 +0.75%p, 전체 +1.00%p, 풀세트 최대 +10%**로 승인할지 결정한다. 개별 조건 또는 상한을 바꿀 경우 해당 항목과 목표 범위를 지정한다.
3. 구현 착수에 대해 **승인 / 조건부 승인 / 보류** 중 의견을 받은 뒤 사용자가 최종 결정한다. 조건부 승인이라면 착수 전 충족할 증거를 정하고, 보류라면 수정할 수치나 범위와 재검증 조건을 정한다.
